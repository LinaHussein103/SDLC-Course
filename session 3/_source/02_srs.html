1Project overview

System name: University Library Reservation and Borrowing System.

Description. Students can browse books, search the catalogue, check availability, reserve books and monitor their borrowing status through a digital system. The student must physically visit the university library to collect and return books. Librarians handle physical preparation, collection and return confirmation.

Objectives

  • Reduce unnecessary library visits.
  • Improve book discovery.
  • Allow digital reservations.
  • Prevent conflicting reservations.
  • Improve loan tracking.
  • Automate reminders and availability notifications.
  • Improve librarians’ operational efficiency.

Key terms

  • Book (title) — a bibliographic record, e.g. “Clean Code”.
  • Copy — one physical item of that book with its own barcode.
  • Reservation — a request that holds a specific copy for a student.
  • Loan — a copy that has been physically handed over to a student.
  • Waitlist — a queue of students waiting for any copy of a title.

2User roles and permissions

Guest — anyone, not signed in. Can browse and search the public catalogue without authentication.

Student — an authenticated, enrolled student. Can reserve books, view loans, receive notifications and monitor fines.

Librarian — library staff. Views student reservations, prepares books, confirms collection and returns, manages copy availability and monitors borrowing periods.

Administrator — manages policies (loan length, fine rates), staff permissions and system configuration.

CapabilityGuestStudentLibrarianAdmin
Browse & search the public catalogue✓✓✓✓
Reserve a copy / join a waitlist / cancel own reservation—✓ own——
View loans, due dates, fines and notifications—✓ own✓ all students— (audit only)

Configure policies, fine rates, staff roles, calendars———✓
Why separate permissions? The principle of least privilege: each role gets only what it needs. A student sees only their own data; a librarian cannot change the fine policy; an administrator does not process day-to-day loans.

Race conditions — why “check, then save” is not enough

Sara and Yazan both open the last available copy of Introduction to Algorithms. At 10:00:01 both apps check: “1 copy available”. Both press Reserve. If the system checks availability and saves the reservation as two separate steps, both requests can pass the check — and two students are promised one book.
Requirement: the availability check and the reservation write must happen inside one atomic database transaction, protected by a uniqueness rule (only one active reservation per copy). The first request wins; the second receives a clear message and an offer to join the waitlist. UI checks alone can never prevent this, because the conflict happens on the server.

7Database requirements (conceptual)

A conceptual model shows what data the system needs and how it relates — not how tables are implemented. No SQL is part of this specification.

PK primary key · FK foreign key · 1 / N one-to-many · 0..1 at most one

Supporting entityPurpose (summary)
StaffAccountsLibrarians and administrators: StaffID, name, role, active flag. Linked to the university identity service; roles drive permissions.
PoliciesConfigurable values with effective dates: loan days, reservation expiry hours, fine rate, maximum loans, collection hours, closures.
AuditLogsAppend-only record of important actions: who (StaffID/StudentID), what (action, entity, old → new status), when (timestamp).

Primary key (PK) — a value that uniquely identifies one row, e.g. CopyID.

Foreign key (FK) — a column that points to another entity’s PK, e.g. Loans.CopyID → BookCopies.CopyID.

One-to-many — one student can have many loans; each loan belongs to exactly one student.

Books vs. copies — “Clean Code” is one Book with several BookCopies. Students reserve and borrow copies; they wait for books (any copy).

Referential integrity — an FK must always point to an existing row; a copy cannot be deleted while a loan refers to it.

Atomic transactions — related changes (reservation → loan, copy status) succeed or fail together (BR-10).

No duplicate active reservations — a uniqueness rule allows at most one active reservation per CopyID (FR-10, BR-04).

Dates & times — store timestamps in UTC with time-zone awareness; display in local time (Asia/Amman). Due dates are calculated with the academic calendar.

9Edge cases and expected behaviour

#ScenarioExpected system behaviour
E1Two students reserve the final copy simultaneouslyOne atomic transaction succeeds; the other student sees “This copy was just reserved” and is offered the waitlist (FR-10, BR-04).
E2Student authentication failsClear, non-technical message; retry or help link; the selected book is kept for after sign-in (FR-08).
E3Student becomes ineligible while a reservation is pendingReservation is flagged for the librarian and not handed over; the student is notified with the reason and next steps (BR-08).
E4Reservation expires before collectionAfter 48 h the reservation becomes “Expired”, the student is informed and the copy goes to the next waitlisted student or back to available (BR-02, BR-07).
E5A student does not receive a notificationAll notifications are also visible in the in-app list (FR-18); failed deliveries are logged and retried.
E6A book is reported lost or damagedLibrarian records the condition (FR-24); the copy leaves circulation; affected reservations are reallocated or the students notified.
E7A student returns a book lateReturn is recorded normally; the fine is calculated by configured policy (FR-27) and shown with days overdue and rate.
E8Connectivity is lost while reservingNo reservation is created unless the server confirms it; the app shows the true status on reconnect and never shows a false success.
E9An overdue book is returned while a fine is outstandingThe loan closes; the fine stays “Outstanding” until settled under university policy, and remains visible to the student.
E10A copy is returned while students are waiting for that titleThe copy is allocated to the first eligible waitlisted student before anyone else can reserve it (BR-07, FR-15).
From requirements to design. Every screen in the UI/UX exercise should trace back to at least one requirement above. When you critique or redesign a screen, ask: which FR, BR or NFR does this element serve — and does the design make that requirement easy for a real user?
